# Devlog

## 2025-09-04 09:28:56 +0100 — commit `06c3638`

Commit `06c36380d627dcbfd2e0a9ed0e17967d9540cf39` is the point where the repository stops treating the API gateway as a future edge component and turns it into a concrete Spring Boot service wired into the local runtime. The evidence in `changed-files.txt` shows that the work was concentrated in `api-gateway/`, `docker-compose.yml`, and `services/authentication-service/README.md`, with two additional NetBeans cache files changed under `services/matching-engine/` and `services/orders-service/`. Those cache-file diffs are binary in `diff.patch`, so their exact semantic effect is not observable from this evidence set.

Before this commit, `docker-compose.yml` still kept `api-gateway` behind `profiles: ["later"]`, which meant the gateway service was described in the stack file but not part of the default runtime path. After `06c3638`, that profile gate was removed and the service became a normal always-on part of the compose topology. The compose section was also tightened structurally: `ports` was normalized to `["8080:8080"]`, `depends_on` was rewritten into compact health-checked mappings for `auth-service`, `user-registration-service`, and `redis`, and the environment block was expanded to carry `AUTH_BASE_URL`, `REG_BASE_URL`, `ORDERS_BASE_URL`, `JWT_PUBLIC_KEY_LOCATION`, and `REDIS_HOST`. This changed the gateway from a deferred shell into a container expected to start against the same service graph as the rest of the platform. The same compose edit mounted the `jwt_public.pem` secret into the gateway and retained an actuator healthcheck on `http://localhost:8080/actuator/health`, which is consistent with the new code added under `api-gateway/`.

The gateway implementation itself did not exist in observable form before this commit because every Java source file listed in `changed-files.txt` appears in `diff.patch` as a new file. `api-gateway/pom.xml` establishes the service as a Spring Boot 3.3.3 / Java 21 application with Spring Cloud 2023.0.3. The dependency selection is specific rather than generic. `spring-cloud-starter-gateway` provides the reactive edge proxy, `spring-boot-starter-oauth2-resource-server` makes the service a JWT-verifying resource server, `spring-boot-starter-data-redis-reactive` supports Redis-backed rate limiting, `spring-cloud-starter-circuitbreaker-reactor-resilience4j` adds circuit-breaker support at the route layer, and `spring-boot-starter-actuator` exposes health and metrics endpoints. In before → after terms, the repository moved from having only downstream services plus compose declarations to having an actual buildable Maven gateway service with explicit operational and security dependencies.

`api-gateway/src/main/java/com/tradestream/gateway/ApiGatewayApplication.java` is the minimal bootstrap class for that new module. This file does not add business logic, but its presence is the formal transition from configuration-only intent to a runnable Spring Boot application entry point. The more meaningful functional additions are in the filters, security, and route configuration.

`api-gateway/src/main/java/com/tradestream/gateway/filters/RequestIdFilter.java` introduced a global request ID behavior at the edge. Before this commit, there is no gateway code in the evidence that could ensure correlation IDs existed. After the commit, every request passing through the gateway can be guaranteed an `X-Request-Id` header because the filter checks for an existing value and, if absent, mutates the request with a generated UUID. This is a small file, but it is a concrete operational change: the edge starts standardizing request tracing rather than leaving that concern to downstream services or external proxies.

`api-gateway/src/main/java/com/tradestream/gateway/ratelimit/RateLimitConfig.java` adds an IP-based `KeyResolver` for rate limiting. The implementation prefers the first entry from `X-Forwarded-For` and falls back to the remote socket address, then finally to `"unknown"`. That means the initial rate-limit identity model is network-origin based rather than user- or token-based. The evidence does not show the Redis rate limiter parameters themselves in Java code, but the presence of this resolver and the Redis dependency makes it clear that the gateway now has the internal pieces needed for per-client throttling on selected routes.

`api-gateway/src/main/java/com/tradestream/gateway/security/SecurityConfig.java` is the main security boundary introduced by the commit. Before this file existed, there was no code in the gateway to distinguish public and protected paths. After the commit, the service applies a reactive deny-by-default posture. The configuration explicitly permits `GET /actuator/health` and `GET /actuator/info`, permits `POST /api/auth/login`, `POST /api/auth/refresh`, and `POST /api/users/register`, and requires authentication for everything else. The JWT converter logic is also specific: it reads scopes from either a `scopes` claim or a `scope` claim, normalizes them into a collection, and converts them into `SCOPE_*` authorities. That matters because it defines the gateway’s expected token shape and shows that the new edge layer is meant to enforce authorization based on claims rather than simply pass through bearer tokens opaque to the system.

`api-gateway/src/main/java/com/tradestream/gateway/web/FallbackController.java` adds a simple `/fallback` endpoint that returns JSON with `status: "degraded"` and a retry-oriented message. This is tied directly to the route-level circuit breakers later defined in `application.yml`. The before state had no observable fallback path because there was no gateway application at all. The after state introduces a standard degraded response contract whenever downstream circuit breakers open.

The largest functional change in the chunk is `api-gateway/src/main/resources/application.yml`. This file turns the gateway from a generic Spring Boot app into a route coordinator for the existing microservices. The beginning of the file sets `server.port: 8080`, names the app `api-gateway`, and points JWT verification at `file:/run/secrets/jwt_public.pem` by default via the `spring.security.oauth2.resourceserver.jwt.public-key-location` path. Default gateway filters remove cookie headers and deduplicate CORS headers, which indicates an early decision to keep the edge stateless and to reduce duplicate browser-facing header output.

The route table then wires specific external paths to internal services. `POST /api/auth/login` is proxied to `http://auth-service:8082/login` and rate-limited. `POST /api/auth/refresh` is also sent to `auth-service`, but the route injects `X-Internal-Caller: api-gateway` before forwarding to `/refresh`. That is an important before → after change when read alongside the earlier authentication-service work in this repository: the refresh endpoint’s internal-caller requirement now has a concrete upstream component that satisfies it automatically. `POST /api/users/register` is similarly rewritten to `http://user-registration-service:8081/register` with `X-Internal-Caller: api-gateway`, so registration also becomes an edge-mediated internal call rather than a direct client-to-service interaction.

The rest of the route map shows the gateway becoming the common entry point for the domain services that already existed elsewhere in the repo. `/api/orders/**` is rewritten to `/api/orders/${p}` on `orders-service` and wrapped in a circuit breaker named `ordersCB` with `fallbackUri=forward:/fallback`. `/api/transactions/**` is rewritten onto `transaction-processor` with `txCB`. `/api/portfolio/**` is rewritten to `/portfolio/${p}` on `portfolio-service` with `portfolioCB`. `/api/market-data/**` is rewritten to `/candles/${p}` on `market-data-consumer` with `mdCB`. That last mapping is especially specific: the public namespace is normalized to `/api/market-data/**`, while the backing service still exposes candle-oriented routes. This is a concrete example of the gateway beginning to shape a stable public API independently from downstream path design.

The same YAML file also defines permissive global CORS for all paths, exposing `X-Request-Id`, and turns on actuator exposure for `health`, `info`, `gateway`, and `metrics`. Finally, it configures four Resilience4j circuit breakers, all with count-based sliding windows of 20 requests and a `failureRateThreshold` of 50. The evidence does not show custom timeout or half-open tuning, so the initial gateway resilience model is broad but shallow: every core downstream service gets a breaker, but the breaker policy is uniform and minimal.

The commit also introduces `api-gateway/Dockerfile`, which packages the service as a Java 21 runtime image. The file copies the built JAR into `/app/app.jar`, exposes port `8080`, and performs container health checks against `/actuator/health`. This aligns with the compose activation described earlier. Before the commit, compose referenced a gateway build context, but there was no observable Dockerfile in the diff evidence for a runnable gateway image. After the commit, the service has the full chain required for local deployment: Maven build, application entry point, configuration, container image, and compose integration.

The only non-gateway source file with a textual diff in this chunk is `services/authentication-service/README.md`, and the change is large. Before `06c3638`, the README framed the service in terms of signed access tokens and encrypted refresh tokens, explicitly claimed JWE-based refresh-token handling, referenced AES-256-GCM encryption performed by the API gateway, and used a badge-heavy format. After the commit, the README is rewritten into a much more structured “Source of Truth” document. The new version describes the service as a stateless authentication microservice issuing RSA-signed JWTs with PS256, explains `/login` and `/refresh`, documents the `X-Internal-Caller: api-gateway` gate, spells out access and refresh TTLs, lists the environment variables, includes operational commands, and adds CV/interview-oriented sections. The before → after shift is not just cosmetic. It changes the documented architecture from one centered on encrypted refresh-token wrapping to one centered on signed JWT issuance plus gateway-mediated refresh access. Because this rewrite lands in the same commit as the gateway code that forwards `/refresh` and `/register` with the internal caller header, the documentation and runtime edge behavior become much more aligned than they were previously.

There is still some uncertainty inside that README rewrite. The diff shows a very assertive source-of-truth document, but the chunk evidence here only directly proves the gateway code and the README text itself. It does not, by itself, verify every operational claim embedded in the README, such as broader CV-style impact statements or all of the troubleshooting guidance. What is grounded from this chunk is that the documentation was rewritten to present the authentication service in a more precise, gateway-integrated form, and that several of those claims, especially the internal refresh gate and JWT signing model, are consistent with the new edge configuration introduced in the same commit.

The two remaining file changes listed in `changed-files.txt` are `services/matching-engine/nb-configuration.xml` and `services/orders-service/nb-configuration.xml`. `diff.patch` represents these as binary differences, so their exact content is not inspectable from the allowed evidence. Chronologically, `06c3638` reads as a single broad integration commit rather than a series of narrowly separated refinements. The repository had already accumulated downstream services, but the public edge was still absent as executable code and disabled in compose. After this commit, the system gained a concrete API gateway service with JWT verification, route rewriting, header injection for internal-only auth and registration flows, Redis-backed rate-limit infrastructure, circuit-breaker fallbacks, request ID propagation, container packaging, and default participation in the local stack. At the same time, the authentication-service README was rewritten to match that new edge-mediated architecture more closely than the older badge-and-crypto-description version did.
